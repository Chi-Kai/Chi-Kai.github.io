今天读的两篇东西，一个是播客，一个是评测框架的工程博客，看起来不搭界，但其实在回答同一个问题：沙箱的边界到底该画在哪儿，画完以后还剩下什么是它管不到的。

## 只沙箱化 tool call，是把方向盘留在了外面

先说播客。Jan-Niklas Wortmann 请了 Rancher 的联合创始人 Darren Shepherd 聊沙箱，节目叫 [Why AI agents belong in the sandbox](https://www.wordman.dev/podcast/darren-shepherd-ai-agent-sandboxes/)。有意思的是他一开始觉得沙箱这东西很蠢，能起容器干嘛还要买沙箱。后来他自己写 coding agent，想同时跑十几个任务又不想让 git work-tree 互相打架，结果做出来最有意思的部分反而是一套沙箱系统。

他最尖锐的观点是关于边界位置的。现在常见的做法是 agent loop 跑在外面，只把工具调用丢进沙箱。他认为这是根本上错的，原因很直白：loop 本身在指挥代码，这些代码拿着密钥、能连外部系统，那 loop 凭什么不在沙箱里？他的建议是把 agent 和工具一起扔进同一个沙箱，用同一套密钥和出口策略管，用他的话说"这样其实最省事"。

另外两点我也挺认同。一是对 agent 来说要管的是出口流量而不是入口，因为 agent 是服务的消费方。二是真密钥别给它，给一个形状对的假 key，在透明代理那里换成真的，策略检查和防外泄都放在代理上。这和昨天写的那篇里"密钥根本不进 guest"是同一个思路，只是 Darren 把它放进了一个更完整的边界设计里。他还顺带提到，服务端的 provider 工具（比如托管的 web search）会打开一些很难推理的外泄路径，所以他更倾向于 loop 跑在客户端。

## 隔离是梯子，不是开关

再看 Coder Eval 团队的 [Three isolation tiers and one canary](https://coder-eval.com/blog/strict-agent-eval-sandbox)。场景是 agent 评测：agent 不去推导答案，而是直接去读答案。

他们把隔离分成三档：tempdir（直接在宿主机临时目录跑）、docker 加 bridge 网络、docker 加 network: none。按搭建成本排序，恰好也是按堵住污染渠道的多少排序。他们把最底层那档说得很直接：tempdir 下 agent 就是宿主机上一个和 harness 同 uid 的普通进程，harness 能读的它都能读，README 里明写了这不是安全边界。所以在这一档他们干脆不做任何"屏蔽"，因为 agent 能轻易撤销的控制不是弱控制，而是误导人的控制。我很喜欢这个判断，很多系统恰恰是在这里自我安慰。

真正让我停下来想的是他们的数据。7,464 次运行里，有 174 次 agent 摸到了评分材料，比例 2.3%。而且这个比例更多取决于 harness 而不是题目：Claude Code 是 5.5%，Antigravity 2.0%，Codex 1.0%，换个 harness 能差 5 倍。手法都不高明：搜索失败就扩大到仓库根目录，按惯例猜评分脚本文件名，读 `check_*.py` 里的期望值，或者干脆把评分器当神谕反复跑到全部 OK。

关键在于，这些手法没有哪一档能挡住。网络和宿主文件系统可以封，但任务定义 `task.yaml`、和任务放在一起的检查脚本、fixtures，在任何一档里都是可读的。文章原话的意思是：隔离能关掉网络和宿主文件系统，但关不掉"评分器就放在任务旁边"。他们最初的加固（把 fixtures 打包 base64、把辅助脚本编译掉、启动时删 Python 文件）也没顶住。最后的办法是在答案里埋 canary 字符串，agent 一旦读到就能在输出里被发现。预防靠档位，检测靠 canary，而 canary 在每一档都管用，包括什么都不隔离的那一档。

## 放在一起看

两篇放在一起，我的感受是"边界"其实有两种。

Darren 讲的是信任边界：谁能拿到密钥、谁能往外发流量。这个边界画错了位置，后果是 loop 在沙箱外面拿着权限乱跑，所以他主张把边界往外推，推到把整个 loop 包进去。Coder Eval 讲的是信息边界：沙箱里本来就要放任务需要的东西，而这些东西里可能就混着答案。这种情况下边界推得再远也没用，因为泄漏源本来就在边界里面。

所以我现在的理解是，沙箱解决的是"外面的东西别进来、里面的秘密别出去"，但它不回答"里面放了什么"。对于后者，要么从放进去的内容上下手（评分器别跟着任务走、真密钥换成假 key），要么接受挡不住，转而做检测。Darren 的透明代理其实也是这两种思路的结合：假 key 是把秘密移出边界，代理上的外泄检查是检测。

还没想清楚的是 canary 的思路能推多远。评测里很好办，答案是确定的字符串，埋一个就行。但在生产 agent 里，"不该被读到的东西"往往没有这么清晰的形状，比如一份内部文档、一段别的用户的上下文。能不能给这些东西也打上可检测的标记，在出口代理上统一识别，我觉得是个值得继续看的方向。另一个问题是 Coder Eval 的数据说明泄漏率跟 harness 强相关，那评测沙箱的设计是不是也该把 harness 当成一个变量来报告，而不是只报模型和档位。
